# 推测解码验证台（Speculative Decoding Verifier）

用 FastAPI + CPU 版 PyTorch 实现的网页应用，验证**推测解码能否在保证输出完全一致的
前提下节省目标模型的前向调用**，并验证**被拒绝的草稿不会污染后续生成**。

另附**下一字符校准台**：录入人工核实的「提示词 → 真实下一字符」样本，用固定目标模型
的真值概率做 split conformal 校准，输出可打印 ASCII 下一字符预测集合，帮助研究员
判断哪些提示词还需人工复核。

所有模型权重在进程内以固定随机种子生成，**无需下载任何模型**；词表为固定的 98 个
字符级 token，草稿与目标模型共用。

## 目录结构

```

  decoding.py      无缓存逐 token 贪心基线 与 带 KV 缓存的推测解码
  calibration.py   split conformal 校准：样本批次/修订号、共形分位数、后台计算任务
  main.py          FastAPI 路由（解码对照 + 校准）、固定预设
static/
  index.html       解码对照单页（对照输出、逐轮接受数、前向次数、首处分歧标记）
  calibration.html 校准单页（样本编辑、计算发起、按修订号标记的预测集合）

```

## 模型设计（均为固定权重、确定性可复现）

| 模型 | 层数 | 注意力头 | d_model | 说明 |
|---|---|---|---|---|
| 目标模型 | 4 | 4 | 128 | 被核验的大模型 |
| 草稿模型 | 1 | 2 | 128 | 提议草稿的小模型 |

- 二者**共享 token 嵌入与 LM head（权重绑定）**，词表共用；
- 草稿主体在同一初始化 RNG 流之后，再用独立固定种子（seed=99）注入受控高斯扰动
  （σ=0.125）。该尺度经实测使两模型首 token 预测翻转率约 30%，从而同一服务内
  既能稳定观测到**整块接受**，也能稳定观测到**拒绝**；
- 完全独立初始化会导致未训练模型 argmax 近乎 100% 不同（几乎全拒绝），完全一致
  又不会拒绝，受控扰动是让两条路径都可演示的关键。

## 推测解码算法要点

1. 用户设置每轮草稿数 `k ∈ [1,4]`、最多新 token 数 `max_new ∈ [1,32]`；
2. 每轮草稿模型基于**自身 KV 缓存**逐 token 增量写出最多 `k` 个草稿；
3. **目标模型每轮只做 1 次前向**，整块核验草稿；首轮输入「提示词+草稿块」，
   之后每轮输入「上一轮 pending 的纠正/补词 token + 新草稿块」，
   **已缓存前缀绝不重算**；
4. 逐位比对目标贪心预测与草稿 token：
   - 拒绝：丢弃被拒位置及之后的草稿，采用目标在该位置的纠正 token，并把目标/草稿
     KV 缓存截断回滚到接受前缀（回滚无污染，有专项测试）；
   - 整块接受：额外采用目标基于整块上下文的补词 token；
5. `max_new` 上限与 EOS 截断在两条路径上语义完全一致（EOS 计入输出，其后停止）；
6. argmax 平局取词表序号小者（`torch.argmax` 返回首个最大值，天然满足）。

**缓存不变量**：每轮开始时目标缓存覆盖确认前缀倒数第二个 token，pending 保存上一轮
tail；草稿缓存对齐完整确认前缀。因此目标前向次数恒等于推测轮数。

## 下一字符校准台（/calibration）

文本生成研究员录入人工核实的下一字符样本，判断哪些提示词还需复核。

### 录入与计算

- 样本批次：**10～30 条**，每条 = 提示词（1～32 个可打印 ASCII）+ 真实下一字符
  （恰好 1 个可打印 ASCII）；服务端逐条校验并返回中文明细；
- 错误率 **α ∈ {0.1, 0.2}**；待判提示词每次 1～20 条（同样 1～32 可打印 ASCII）；
- 用**固定目标模型**计算真值概率（全词表 log-softmax，float64），非一致性分数
  **s = −ln P(真实下一字符 | 提示词)**。该分数与经典的 1−P 分数**严格单调等价**
  （精确算术下二者给出的预测集合完全相同，有专项测试锁定）；选用对数域是因为本
  目标模型置信度极高（真值概率可低至 1e-40 以下），1−P 在 float32/float64 下都会
  饱和成精确的 1.0，丢失全部区分度；
- **有限样本修正分位数**：k = ⌈(n+1)(1−α)⌉（用分数做精确整数运算，规避
  20×0.8=16.000000000000004 这类浮点取整陷阱），q̂ 取第 k 小的校准分数；
- **预测集合** C(x) = { c ∈ 95 个可打印 ASCII : −ln P(c|x) ≤ q̂ }：
  分数相等的字符**全部纳入**（≤ 比较，不做随机拆分）；**集合为空时如实返回 ∅**
  （本模型几乎必然饱和、空集在自然数据下罕见，但空集路径有合成数据单测覆盖）；
- 复核启发式（纯展示，不属于覆盖率保证）：空集或集合覆盖过半可打印字符 → 建议复核。

### 并发与版本语义

- 样本批次带**修订号**：两个窗口同时编辑时，提交必须携带所见修订号
  （`base_revision`）；修订号不匹配返回 **409 且不覆盖**服务器数据；
- 计算在**后台线程**进行，**计算期间仍可提交样本修订**；
- 计算结果永远**标记其基于的样本修订号**：样本随后被修订时，旧结果保留但页面
  显示「已过时」横幅——旧版计算**不冒充**当前样本的结论；
- 计算**失败时保留标有修订号的上次成功结果**，页面同时展示失败原因；
- 同一时刻只允许一个计算任务（进行中再发起返回 409），样本修订不受此限。

### 与原解码的隔离

校准只读使用目标模型：旁路前向走 `use_cache=False`（不触碰 KV 缓存），并通过
线程本地的 `forward_count_suspended()` 暂停本线程前向计数。**模型权重、KV 缓存、
原解码的前向计数均不受影响**，校准计算进行中解码接口照常可用（有并发专项测试：
校准线程被阻塞期间，基线+推测解码的结果与前向计数与参照完全一致）。

## 正确性保证

推测解码输出在拒绝、整块接受、EOS、达到上限等所有情况下，都与「目标模型**无缓存、
逐 token、对完整前缀重算**的贪心基线」**逐 token 完全相同**。前端在不一致时会标出
首个分歧位置（token id 与文本）并判定 FAIL。

## 启动方式

### Docker Compose（推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000        （推测解码验证台）
# 浏览器打开 http://localhost:8000/calibration （下一字符校准台）
```

镜像基于 `python:3.11-slim`，通过 PyTorch 官方 CPU index 安装
`torch==2.5.1+cpu`，不含 CUDA 依赖；带 `/api/health` 健康检查。

```bash
pip install --index-url https://download.pytorch.org/whl/cpu torch
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 接口

- `GET /api/health`：服务与模型信息；
- `GET /api/presets`：返回固定的「拒绝」「整块接受」两条预设提示词；
- `POST /api/decode`：入参 `{prompt, k(1~4), max_new(1~32)}`，返回两种方式的
  token 序列、解码文本、目标/草稿前向次数、逐轮核验明细、节省统计与一致性判定；
- `GET /calibration`：校准单页；
- `GET /api/calibration/state`：样本批次、修订号、当前任务状态、上次成功结果
  （含其修订号与 stale 标记）；
- `PUT /api/calibration/samples`：整批提交样本 `{base_revision, samples}`；
  成功返回新修订号，修订冲突返回 409（不覆盖），样本不合法返回 400（逐条明细）；
- `POST /api/calibration/compute`：入参 `{alpha(0.1|0.2), test_prompts}`，
  202 发起后台计算（基于当前修订号快照）；任务进行中或参数不合法返回 409/400。

## 实测结果（CPU，torch 2.5.1+cpu，单线程）

解码测试命令：`python tests/test_decoding.py`，**11 项全部通过**。
校准测试命令：`python tests/test_calibration.py`，**13 项全部通过**。

- 84 组参数组合（7 提示词 × 4 个 k × 3 个 max_new）下，推测解码与贪心基线
  逐 token 完全一致；
- 缓存/无缓存两条前向路径的 argmax 决策逐位相同（logits 仅 ~1e-5 级 float32
  舍入差异）；缓存回滚后续写与整序列前向逐位一致；
- 前向次数（k=4、max_new=32）：
  - 整块接受预设：基线 **32** 次目标前向 → 推测 **7** 次（减少约 78%）；
  - 拒绝预设（首轮接受后持续被拒）：基线 32 次 → 推测 **28** 次，且输出仍与
    基线完全一致，证明被拒草稿未污染后续生成；
- 强制注入 EOS 后，4 个 k × 3 个上限组合下两条路径 EOS 位置与截断完全一致；
- FastAPI TestClient 与真实 `uvicorn` 启动均验证通过，参数越界返回 422、
  空提示词返回 400。

校准实测（`tests/test_calibration.py` + 真实 uvicorn 冒烟）：

- 分位序号 k 精确整数计算（含 n=19、α=0.2 的浮点陷阱用例）；−lnP 与 1−P 分数的
  预测集合一致性有专项测试；
- 双窗口场景：过期修订号提交被拒（409）且服务器数据未被覆盖；计算进行中提交
  新修订成功，旧版结果标记修订号并判为过时；计算失败后上次成功结果原样保留；
- 隔离性：校准前后目标/草稿模型的 KV 缓存逐张量相等、前向计数不变；校准线程
  被阻塞期间解码结果与前向计数和参照完全一致；
- 端到端：示例批次（12 条）α=0.1 时 q̂≈100.6 nats，待判集合 86～92/95；
  样本真实字符取模型 top-1 时集合收缩为单字符。

> 说明：拒绝预设的前向节省为负向示例——当草稿质量差时推测解码不会节省调用，
> 这正是本验证台要展示的权衡；输出正确性不受影响。
